# Design

## Context

Greenfield repository: only REQUIREMENTS.md, README.md and OpenSpec scaffolding exist. No server, adapter or Amazon integration exists, and nothing has been tested on a real account. Motivation and scope are in `proposal.md`; behavior contracts are in `specs/`. This design covers Milestone A (REQUIREMENTS.md §12) only; the remaining MVP scope is in `openspec/ROADMAP.md`.

## Goals / Non-Goals

**Goals:**
- Smallest bounded, testable proof harness (Node.js/TypeScript, strict) to answer Milestone A questions with evidence.
- Shape the code so adapter, session manager and operation journal can be reused in Milestone B (ARCH-02, ARCH-03, §14 light interfaces: `AlexaAdapter`, `CredentialStore`, `OperationStore`).
- Make every unknown explicit rather than assumed.

**Non-Goals:**
- No MCP server, HTTP transport, authorization, SQLite product schema, packaging, public docs or release.
- No distributed components or generic frameworks.

## Decisions

1. **Library pinning.** Select alexa-remote2 and its cookie helper by reviewing current releases and fixes, then pin exact versions with a lockfile. 8.1.1 / alexa-cookie 5.0.6 are only the inspected references (§2, §15). Alternative: float to latest; rejected because behavior is undocumented.
2. **Thin adapter over callbacks.** Promise-wrapping adapter that normalizes outputs to the outcome vocabulary and passes unknown fields through as inert data. No generic "call any method" or raw HTTP surface (CAP-02).
3. **Credentials.** Session file in a protected directory outside the repo, atomic write (temp file + rename), owner-only permissions (ACL on Windows, 0600 on Linux), git-ignored. One session manager owns initialization, refresh and setup with an in-flight operation shared by callers. Encryption at rest is evaluated, not assumed; an adjacent key file is not counted as protection (AUTH-03). Login proxy binds loopback only, time-limited, separate from any later MCP route. Alternative: environment-variable cookies; rejected as they leak into process listings and logs.

   The pinned library can fall back to cookie generation after refresh failure, reinitialize on rejected authentication, and start its own refresh timer; its helper defaults to a non-loopback proxy bind. Patch the pinned authentication lifecycle to prevent implicit login or reinitialization and disable the upstream refresh timer. Require the patch and fail closed if it is missing or incompatible. The session manager invokes the supported interactive login flow only for an explicitly approved setup window, with a loopback bind enforced before the helper starts. Expiry or cancellation must prevent a delayed proxy start, stop any listener and prevent later callbacks from persisting a session. No live initialization, refresh, login or authentication preflight occurs without matching owner approval. Offline tests exercise the actual patched paths for refresh failure, authentication rejection, network failure, timer suppression, delayed startup and expiry.
4. **Redaction at the source.** A single logger wrapper redacts known secret keys and patterns; evidence is generated by a sanitizer that maps real names/ids to synthetic labels, with the mapping kept in an ignored local file (SEC-06).
5. **Nested-retry inspection (REL-03).** Step 1: read the pinned source for retry, re-login, and error paths beneath each method used. Step 2: build a local fake HTTP endpoint and fault-injection tests that count requests per logical write for timeout, reset, 5xx and 401. Step 3: if a write can be resent internally, disable via configuration or patch/wrap so at most one dispatch occurs, and block live write probes until this passes. Outer retries apply only to reads and proven pre-dispatch failures (REL-04). Alternative: add outer policy only; rejected because it cannot control inner resends.
6. **Journal.** Minimal local file-based or SQLite record written before dispatch and updated after (REL-06); incomplete records recover as `unknown`, never replayed. SQLite choice is not final for the product (ARCH-04), so this stays behind `OperationStore`.
7. **Owner-approved live testing.** Live probes are separate CLI entry points that refuse to run without a local approval file naming probe, targets, parameters and expiry, created by the owner by hand. Live tests never run in CI or default test scripts. Order: sign-in, read-only reads, state read, DND read, harmless mutation, routine, DND write/recovery. Each step is stopped if the previous reveals a blocker.
8. **DND recovery.** Snapshot-before-write, restore-original (not disable), conservative conflict policy: skip restore when the current value is not the value this probe set (TEMP-02, 05, 07). Equality alone does not prove there was no manual away-and-back change. Use upstream revisions/history when available; otherwise document the attribution limit, stop automatic restoration on uncertainty, and obtain owner direction rather than claim perfect compare-and-swap (TEMP-05). Native duration behavior is observed and recorded, not assumed (TEMP-03).
9. **Alexa+ uncertainty.** Status is an input recorded by the owner plus observation, not inferred. Results are recorded per operation with date, version and sanitized environment, with `untested` as a first-class value (PLUS-01, 05).
10. **Evidence document.** A sanitized, dated document records results, stating one account/device set was used and that it is not certification (§2, OSS-07). Final deliverable is a go/no-go note.

## Risks / Trade-offs

- Amazon login may be blocked or change → keep owner-driven, stop at first failure, record as blocker, no retry loops.
- Account lockout or suspicious-activity flags from repeated attempts → rate-limit attempts, minimize live runs.
- Nested retries cannot be fully disabled upstream → wrap/patch or exclude that write from the product; record decision.
- Probe causes a real-world effect → only harmless, reversible, owner-chosen device; exact-parameter approval.
- Evidence leaks household data → sanitizer plus manual review plus secret scanning before any commit.
- Prototype code tempting to become product → keep interfaces small, review before reuse in Milestone B.

- Whether the event API is probed in Milestone A or deferred.
