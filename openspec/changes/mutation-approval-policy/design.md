# Design

## Context

Milestone B has one tool, `set_light`, and `evaluateMutationPolicy` in `src\mutation-policy.ts`. It checks an ID allow-list, classifies the device from the inventory, and refuses a fixed list of safety classes and anything that is not a `LIGHT`. `MutationService` then journals and dispatches (with object parameters, 429 retry and an inventory cache). The OAuth issuer, journal and Key Vault store are unchanged by this work.

The MCP 2026-07-28 revision replaces server-initiated requests with MRTR: the server ends the call with an `InputRequiredResult` (`inputRequests`, `requestState`), and the client retries the same request with `inputResponses` and the echoed state. A server must not send an input request the client did not declare support for. The installed SDK is `@modelcontextprotocol/sdk` 1.32.2 and may predate this.

## Goals / Non-Goals

**Goals:**
- One simple setting for allow / approve / deny per category, reads included.
- Owner approval bound to the exact action, using MRTR, stateless on the server.
- Safe default, identical to Milestone B when the new setting is absent.

**Non-Goals:**
- Approval web page, scheduling, routines, per-device modes, rate limiting.
- Live shutter or heater actions without owner approval.

## Decisions

1. **Categories and modes.** Categories come from the existing class tokens: `light`, `cover` (shutter, blind, shade, curtain, awning), `climate` (heater, air conditioner, thermostat, fan), `access` (lock, gate, door, garage), `query` for reads, `other` for everything else including unknown. Modes are `allow`, `approve`, `deny`. Alternative considered: per-device modes; rejected as not simple. The allow-list stays as an optional narrowing filter.
2. **Setting.** `ACTION_POLICY` holds `category=mode` pairs, or one preset: `lights-only` (`query=allow,light=allow`), `lights-allow-rest-approve` (`query=allow,light=allow,cover=approve,climate=approve,access=approve,other=approve`), `read-only` (`query=allow`). Parsing is strict and fails startup on any unknown token. Presets are code constants, so they can be reviewed and tested.
3. **Locks and doors.** `access` is configurable, but the presets never enable it beyond `approve`, and the documentation states that `allow` for `access` is discouraged.
4. **Stateless approval.** Request state is `base64url(payload).HMAC` where the payload holds the subject, device ID, action, value, issued-at and expiry (about 2 minutes), plus a random nonce. The HMAC key is a Key Vault secret. Single use is enforced by recording the nonce in the SQLite journal when the approved operation starts; a reused nonce is rejected. Alternative: server-side pending table; rejected because MRTR is designed to avoid server state, and it would not survive a restart as easily.
5. **Approval wording.** The elicitation message is generated by the server from the resolved device name, the action and the value, never from model text, so a model cannot disguise what is being approved.
6. **Elicitation support.** Read the client's declared capabilities from the initialize or request `_meta`. No elicitation support gives `approval_unsupported`.
7. **Tool shape.** Replace `set_light` with `set_device_state` (`id`, `action`: `on`, `off`, `open`, `close`, `set_brightness`; optional `value`). Keep `set_light` as an alias for one release so existing clients keep working. `open` and `close` need a capability that is not yet verified against the owner's Alexa (see Unresolved).
8. **SDK support.** First task checks what 1.32.2 provides. If it cannot return `InputRequiredResult` from a tool, the server returns the result by a thin handler layer for the `tools/call` response and reads `inputResponses` and `requestState` from the request params. If the negotiated protocol version is older than 2026-07-28, the client cannot use MRTR and is treated as not supporting elicitation (`approval_unsupported`).

## Risks / Trade-offs

- ChatGPT and Claude may not implement MRTR yet. Then `approve` mode is unusable from them and fails closed. Mitigation: verify with each client; an out-of-band approval page is the recorded fallback, not built here.
- A confused agent could ask repeatedly. Mitigation: approval expiry, single-use nonces, and a journal entry per request.
- Approval fatigue: the owner may approve without reading. Mitigation: a clear, server-built message with the device name, action and value.
- Widening beyond lights moves physical risk. Mitigation: deny default, strict parsing, a safe preset, tests for every mode and category pair.
- The signing key is a new secret; rotation invalidates only in-flight approvals.

## Unresolved

- Which Alexa API and capability opens a shutter (power on/off, mode, or percentage) and whether it works through `/api/phoenix/state`. Needs a read of the owner's real shutter capabilities, then an owner-approved live test.
- Whether ChatGPT and Claude currently send the MRTR retry with `inputResponses`.
- Whether `read` requests in `approve` mode make sense. Proposed: allowed for `query` but `approve` is accepted as a value and applied the same way.
